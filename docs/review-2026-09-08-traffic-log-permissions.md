# 2026-09-08 统计更新延迟：日志读取权限

## 现象与根因

- 北京时间02:00报告生成成功；04:00、06:00、08:00定时任务均按时启动，但均报读取独立访问日志失败（EACCES）。页面因此保留02:00快照，04:00是原定下次更新时间，不是数据截止时间。
- 故障时日志为 `nginx:root`、0600；统计任务以root运行，但 `CapabilityBoundingSet=` 清空了能力，不能绕过其他所有者的读取权限。首次发布时只验证了root所有的日志，未覆盖正常日志重开后的所有者变化。
- [Nginx官方说明](https://nginx.org/en/docs/control.html#logs)确认：重新打开日志时，master会将文件所有者指定为worker用户。不将故障中具体所有者变化的时刻作未经证实的推断。
- 定时器没有失效；生成器遇错保留旧报告的机制正常生效。

## 最小修复

只为专用统计日志的root组添加读取权限，将0600改为0640。服务继续清空额外能力，保留无网络、只读文件系统、唯一可写状态目录及原有资源限制。不修改Nginx配置、日志内容或轮转计划，不放宽其他文件权限。

当前生产轮转规则已使用 `create 0664 nginx root`，轮转后的新文件具备root组读取权限；本次修复初建文件遗漏的组读取权限。该现有规则未修改，不能把此次修改描述为未来日志均改成0640。

## 修复前的真实环境验证

在生产服务器创建两次独立临时服务，均以root运行，启用 `NoNewPrivileges`、`PrivateNetwork` 和 `ProtectSystem=strict`；只打开并关闭当前访问日志，不输出日志内容。

| 能力配置 | 实测结果 |
| --- | --- |
| 空集合（原配置） | EACCES，退出1 |
| 仅CAP_DAC_READ_SEARCH | 成功，退出0 |

上述对照确认了根因，但增加系统级读取能力的生产方案被安全审查拦下，未部署。随后检查现有轮转规则，确认可以采用只修改该日志组读取权限的更小范围修复。临时服务使用 `systemd-run --wait --pipe --collect`，执行结束后释放。

## 修复后验收

- 变更前核验专用日志不是符号链接，且仍为 `nginx:root`、0600；只将其改为0640，并预先备份旧报告及历史。
- 手动启动原统计服务成功，退出码为0；服务的能力集合仍为空，无网络、只读系统及唯一状态目录写权限均未改变。
- 北京时间09:12生成新报告，窗口为09月07日08:00至09月08日08:00，包含24个小时桶；下一次计划更新时间为10:00，定时器保持active。
- 未登录线上请求返回401，登录后返回200，响应仍为 `no-store`；Nginx和实验接口服务均为active。
